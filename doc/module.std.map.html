std.map

std.map — the documented API surface of the prelude's Map[K, V]: the keyed store the wordcount exemplar is written against. Stability tier: core.

WHAT IS THE LANGUAGE'S AND WHAT IS STD'S — RULED, and this header stops being a filing. F-0011 asked three questions when this module was written (sc02) and s152 ([type.map], [type.map.key], [mem.map.absent]; wolf-lang#11 item 4, #154) answers two of them and leaves the third exactly as it was:

  • The key protocol: RULED, and there is no Hash half. This header used to say "hashing lives inside the implementations and is unspecified … the Hash half is the filing's open question". [type.map.key] retires that sentence: Map[K, V] admits str, int, char and bool keys this edition — the four whose equality the LANGUAGE defines — and [K: Eq] is satisfied by the four through std.cmp's ordinary impls. So the bound the five functions below already carried is not "the honest half" of a protocol; it is the whole of it. A struct key is E0418 and waits on derived equality, which is named upstream and unruled. impl Eq for char landed in std.cmp at sc44 for this clause: the ruling names four keys and that module shipped three impls.
  • tally: RULED, and it is std's. The filed question was "is absent-key-defaulting a language rule or a std function?" and it closes the way the filing recommended. The LANGUAGE rules the absence — m[k] is V ! {none}, never (); m[k] = v inserts; m[k] op= v is E0417, whose note names map.tally(mut m, k) BY NAME — and STD owns the defaulting. tally's body below is the clause's own spelling, unchanged since sc02 and now ruled rather than proposed.
  • Iteration order: unchanged, and deliberately. keys, values and pairs promise the SAME order as each other for an unmodified map, and nothing more. Both machines answer insertion order at these pins and neither promise is made here.

Map itself stays the language's. The sc02 recommendation — that it become a std-defined generic type — is answered in the other direction and the answer is better than the recommendation: Map is TyKind::Map in the compiler, a wolf_rt::map seam in the native runtime and a served type in the checked machine, so it is a language type with a spec clause instead of scaffolding with a deadline. This module is the API surface over it, which is what §8's container rule has said all along.

LEDGER REALITY at the sc44 pins, measured rather than carried forward. The old paragraph said every function here is unsupported under wolfc because Map is not typed there — "the whole module is, honestly, freight". That is over. What replaced it is not uniform and the differences are the point:

  • The compiler's two rungs TYPE this module now, which means every body in it was read by the mem tier for the first time at this pin. One refusal fell out of that first reading and it is recorded at set below.
  • The [K: Eq] five (get, get_or, has, remove, tally) EXECUTE on the checked tier AND on lupin, as of sc46. They were unsupported on the reference machine for one release, and the reason was never F-0002's old blanket claim: dispatch through a trait declared in the ENTRY FILE ran on all three machines while dispatch through an IMPORTED module's trait was unsupported: Eq is a trait; traits, enums and type-level items have no dynamic semantics here. Measured at sc44 with a twelve-line reduction, filed as wolf-interp#96, and CLOSED in is46 — so F-0002's last quarter goes with it. The three [K: Eq] rows flip unsupported -> run on lupin in this sprint's ledger commit.
  • So the five are FENCED blocks again, which is what sc44 promised would happen "on the wolf-interp release that closes it, and nothing else has to change for that to happen" — nothing else did. Five examples, all five at exit(0) on the reference machine.
  • The native rung refuses this module for a reason that is std.cmp's and not std.map's: impl Eq for Ordering's match (self, other) is unsupported — an enum or row test inside a product pattern (deep trees, c06). Every importer of std.cmp pays it; it is honest and it is older than this sprint.

Absence is spelled none, the convention's own spelling — F-0003 is dead (sc05 pins, renamed at sc06) and nothing here waits on it.

hasfnpub

fn has[K: std.cmp.Eq, V](m: prelude.Map[K, V], k: K) -> bool · regions (ρ1, ρ2) -> -

Whether k is bound. Total: no error row, no traps.

It asks the map itself — the index read m[k], whose none row IS "absent" ([mem.map.absent]) — and allocates nothing. Until sc57 this body walked m.pairs(), which builds a fresh List of every entry in the caller's region on every call: about 6.4 KB a call at 200 entries, never freed in a long-running loop (wolf-std#54, measured on pelt's variable lookups). tests/map/has_allocates_nothing.lu holds the region's ledger at zero across a hit and a miss.

removefnpub

fn remove[K: std.cmp.Eq, V](mut m: prelude.Map[K, V], k: K) -> V ! {none} · regions (ρ1, ρ2) -> ρ_caller

Removes k's entry and returns the value it was bound to; none when the key was absent. No traps.

doctestwolf-doc-example example, run by its own rig

var m = Map[str, int]()
m["a"] = 1
(map.remove(mut m, "a") else 0) == 1
map.has(m, "a") == false
(map.remove(mut m, "a") else 0 - 1) == 0 - 1

Delegates to the language's m.remove(k) ([type.map]; D50 on wolf-lang#11, landed as wolf-lang#344), whose semantics are therefore this function's contract. The erase happens in place. The survivors keep their order, and a miss leaves the map unchanged. Its cost is the clause's: one scan to the key and a shift of the entries after it, with nothing allocated and nothing freed. Until sc52 this body rebuilt the whole map through pairs(), about N^2 entry copies to empty an N-entry map one key at a time. That ran past lupin's and the checked tier's step budgets at 3000 keys (tests/map/remove_many.lu), and the language had shipped the erase a release earlier (B117). The [K: cmp.Eq] bound stays, because it is the module's key protocol ([type.map.key]) and removing it would change the signature. The body no longer calls it.

setfnpub

fn set[K, V](mut m: prelude.Map[K, V], k: K, v: V) · regions (ρ1, ρ2, ρ3) -> -

Binds k to v, replacing any previous binding. Total: no error row, no traps beyond allocation.

The body is m[k] = copy v and the copy is not decoration. This function's body was m[k] = v from sc02 until sc44 and nothing read it, because Map was untyped on both compiler rungs. At the pin that types it the mem tier read it for the first time and answered E1004 — "this stores a value from v's region into m's region — parameter regions are independent by default" — which took the WHOLE module down on both rungs, not just this function. copy is the fix-it the diagnostic itself suggests and it is in the grammar now; the value is copied into the container's region, which for the four key types and every V this edition admits is what a caller means by set.

The asymmetry behind it is filed upstream: (mut xs).push(v) under [T] needs no copy and m[k] = v under [K, V] does, and the same body monomorphic at Map[str, int] runs on all three lanes. Filed as wolf-lang#333; if it is ruled a bug the copy comes back out and no caller notices.

tallyfnpub

fn tally[K: std.cmp.Eq](mut m: prelude.Map[K, int], k: K) -> int · regions (ρ1, ρ2) -> -

Increments the count k is bound to and returns the new count, treating an absent key as zero — the wordcount idiom as a named operation instead of a defaulting index (tally[w] += 1, see the module header's filed question). Traps overflow when the count is at int's maximum: arithmetic is checked in every profile (X3).

The body below is the one [mem.map.absent]'s E0417 note names by name — a reader who writes m[k] += 1 is sent here by the compiler.
