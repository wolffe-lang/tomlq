pkg / std.fs

std.fs

std.fs — the filesystem, over rows: whole texts and whole BYTES, a file-descriptor tier for the streaming cases, directories, metadata, and pure path arithmetic. Stability tier: core.

Errors are rows, never traps (D30, and API-CONVENTIONS §2's trap rule): a missing file, a refused permission, a host failure and a text that is not UTF-8 are all ORDINARY outcomes a caller handles with else or propagates with ?. Nothing in this module traps, and nothing returns a sentinel. The vocabulary is the builtin tier's, adopted verbatim so that std adds no translation layer — s38's five, and s90's three:

  • not_found — the path does not exist (or, on a write, its parent directory does not)
  • denied — the host refused the operation for permission reasons
  • io — every other host failure, coarsened to one tag because no caller can act differently on them yet (§12's rule 3)
  • utf8 — the bytes are not well-formed UTF-8; wolf str is UTF-8 by definition, so a text read that cannot decode is a miss. The BYTE tier below has no utf8 row anywhere, which is its point.
  • eof — a read reached the end of the file, which is an outcome rather than a failure (the fd tier only)
  • exists — the path is already there and the operation demanded to create it (create_dir, and nothing else here)
  • invalid — DECLARED AND UNREACHABLE FROM TYPED CODE since sc35. It named a List[int] element that is not a byte (outside 0..255) offered to a byte write — the WRITE's spelling of the refusal str_from_utf8 makes on the way in (writing is not decoding, so utf8 would be a lie). The byte writes take List[byte] now, so no typed caller can build the argument that raises it; the tag stays in the vocabulary because §14 says the vocabulary is the toolchain's and an FFI caller's wrong-width list still earns it (wolf-lang#231's own posture, adopted verbatim)
  • cross_device — declared by fs_rename and never raised by this module: move_file HANDLES it, which is what the fallback below is for

Capability: fs (I13). Every function here reaches the host filesystem, is tagged fs in the toolchain's sandbox table, and is categorically refused at comptime (D33) — a comptime fn cannot read a file, and the refusal names the reason. s90 widened the surface and did NOT widen the sandbox: the fifteen new builtins carry the same tag and the same categorical refusal. The pure path helpers at the bottom of this module are the exception in both directions: they touch nothing and are comptime-safe.

The three-way split (§8/§9's rule, applied to files). The IMPLEMENTATION owns the builtins this module delegates to — s38's nine (fs_read_text, fs_write_text, fs_open, fs_create, fs_read, fs_write, fs_close, fs_remove, fs_exists) and s90's fifteen (fs_open_mode, fs_read_bytes, fs_write_bytes, fs_read_chunk, fs_write_chunk, fs_read_dir, fs_create_dir, fs_create_dir_all, fs_remove_dir, fs_remove_dir_all, fs_rename, fs_is_file, fs_is_dir, fs_size, fs_modified_ms), s142's fs_fstat, and s199's three (fs_seek, fs_tell, fs_read_at — wolf-lang#426, with the standard streams as handles 0, 1 and 2, #424) — so their semantics are part of this module's contract and are documented per function. std owns everything else: the File value, the consuming close, the mode choice behind append_text/open_append, move_file's fast path and its fallback, and the path arithmetic. The LANGUAGE owns nothing here; there is no file syntax.

Paths are str, forward slashes travel everywhere. wolf has no Path type at v0 and this module does not invent one: a path is a str the host interprets. Write forward slashes in wolf literals on every platform — windows accepts them at the API, and a backslash in a wolf literal is an ESCAPE ("C:\Users" does not lex, seven times over in the s38 test sweep). The path helpers here therefore split on / only, and say so.

THE WORKAROUNDS ARE GONE, AND WHAT REPLACED THEM IS WORTH NAMING (s90, wolf-lang#51/#52, F-0044 and F-0045 both CLOSED). For seven sprints three of this module's functions were shaped by builtins that did not exist, and their docs said so:

  • append_text read the whole file, concatenated in memory and wrote it back, behind an fs_exists check its own doc called a race. It is fs_open_mode(path, 2) + one write + one close now: it touches no existing byte, it asks no question whose answer can change under it, and its utf8 row went with the read that no longer happens.
  • copy_file and move_file were TEXT operations, so a file holding a lone 0x80 did not survive them. Both are byte operations now, and both lost utf8 for the same reason.
  • move_file was copy-then-remove as its ONLY path. fs_rename is the fast path now and copy-then-remove is the FALLBACK, reached through the cross_device row the builtin declares for exactly this purpose.

What is still deliberately absent, each a reviewed contract rather than an approximation:

  • rename(from, to) as an ATOMIC move — WITHDRAWN, not blocked. The contract asked for atomicity; the language deliberately does not promise it, because POSIX rename(2) replaces a destination atomically and windows MoveFileEx is documented to replace but not to replace atomically. Upstream therefore ships fs_rename claiming only the EFFECT and no fs_rename_atomic at all, per the platform rule (a promise that cannot be kept on a tier-1 target does not get a #[cfg] that keeps it on two out of three). std adopts that reading rather than re-promising it one level up: move_file is the wrapper, it says what it does and does not guarantee, and there is no second name for the same call. The one atomically-promisable primitive the language DOES offer everywhere is fs_open_mode's create-new mode, which nothing in std needs yet; the sprint that writes a lock file or a unique temp name wraps it, and this paragraph is where that decision was recorded.
  • stem / extension — a pair that has to decide what a dot means (a leading dot, a doubled extension, no dot at all). That was never a filing about the builtin tier; it is a design question this module has not answered, and the earlier citation of F-0044 beside it was wrong.
  • is_absolute, and join's behaviour on an absolute name — documented on join itself.
  • io.Read/io.Write traits and buffering — blocked on trait dispatch (F-0004), not on the filesystem. Every write here is unbuffered and every function says so.

What this module CANNOT witness, stated rather than implied (§14's rule for a claim a green rig would otherwise imply): denied needs a permission call, cross_device needs two filesystems, and read_dir's utf8 needs a file name the host holds in bytes no str can carry. None of the three has a portable litmus, so no test here observes them; their meanings are documented on the functions and nothing claims more. move_file's fallback is reached only through cross_device, so the TRIGGER is unwitnessed here even though the fallback's body — copy_file then remove — is two tested functions.

Lanes (re-measured at the sc12 pin, one call at a time). BOTH compiler rungs are executing lanes: the checked tier performs real host operations and the native rung lowers all twenty-four fs builtins over the eu ABI (s90, RT_SYMBOLS 83 -> 94), so every new function here lands with two lanes from its first commit rather than gaining the second one later. The comptime sandbox is the one place these operations are refused (D33). lupin has no fs builtins by design, and the refusal for the s90 names is the generic unknown-name one (unsupported: fs_read_dir does not resolve, measured) rather than a reasoned decline — but lupin resolves module bodies LAZILY, so the pure path helpers RUN there:

append_textfnpub

fn append_text(path: str, text: str) -> () ! {IoErrors}

Append text to the end of the file at path, creating it when it is absent.

Rows: not_found when the parent directory does not exist, denied when the host refuses, io for any other host failure. Never traps.

It is an append now, and the three things that used to be true about it are not. Until s90 there was no append-mode open, so this function read the whole file, concatenated in memory and wrote it back — behind an fs_exists check that was a check-then-use race its own doc had to warn about. It opens the file in append mode, writes once and closes:

  • it reads NO existing byte, so its cost is in text rather than in the file's size, and a utf8 row is gone with the decode that no longer happens — appending to a file that is not valid UTF-8 is now an ordinary append;
  • it asks no question whose answer can change before it acts: the create and the open are one host call, so the absent-file case needs no probe;
  • every write lands at the end of the file AS IT IS AT THE MOMENT OF THE WRITE (the mode's whole point), so two processes appending lines to one log no longer lose one of them.

What it still does not promise: that ONE call is atomic. A single short write to an append handle is what the host makes of it, and nothing in the language claims more.

The handle is closed on every exit, including the error path, by a defer — which is the idiom §12 records for exactly this and the reason a failed write here does not leak a descriptor.

Capability fs; refused at comptime (D33). Delegates to fs_open_mode (mode 2), fs_write and fs_close.

doctestwolf-doc-example example, run by its own rig

fs.write_text("doc-append.tmp", "one\n")?
fs.append_text("doc-append.tmp", "two\n")?
(fs.read_text("doc-append.tmp") else "?") == "one\ntwo\n"
fs.remove("doc-append.tmp")?

closefnpub

fn close(take f: self.File) -> () ! {io} · regions (ρ1) -> -

Close f, consuming it.

Rows: io when the handle was already closed or is foreign. Never traps.

take is the mode of the operation's meaning (§3: take only where the value is genuinely gone afterwards): closing ends the handle's life, so the caller spells fs.close(take f) and the compiler rejects every later use of f as a use-after-move. That is the whole staleness story for files, and it costs nothing at run time.

A closed descriptor is never reused by the builtin tier at this pin, so a forged or stale File answers io rather than reaching another caller's file. Do not depend on that beyond this pin: the mode system is the guarantee, the table's behaviour is an implementation detail.

Capability fs; refused at comptime (D33). Delegates to fs_close.

copy_filefnpub

fn copy_file(from: str, to: str) -> () ! {IoErrors}

Copy the BYTES of from to to, replacing to if it exists.

Rows: not_found when from does not exist or to's parent directory does not, denied when the host refuses either half, io for any other host failure. Never traps.

It is a byte copy now, and the row it lost says so. Until s90 it was read_text + write_text, which meant a file holding a lone 0x80 came back refused with utf8 — a copy that works on text and corrupts (or declines) everything else. It is fs_read_bytes + fs_write_bytes, there is no decode anywhere in it, and utf8 is gone from the row because nothing here can raise it.

fs_write_bytes declares invalid for an element that is not a byte. This function cannot raise it: the bytes came out of fs_read_bytes one line earlier and are bytes by construction. The handler below therefore reports io on that arm — the coarsening a caller could not act on differently — rather than widening this signature with a tag no input can reach (§14: a function's row is the union of what its delegates raise, MINUS what it handles itself).

Not atomic, and it reads the whole file into memory: a file larger than the process wants to hold wants the fd tier's read_chunk / write_chunk in a loop. Copying a file onto itself truncates it and is not a supported operation.

Capability fs; refused at comptime (D33).

fs.copy_file("doc-copy-src.tmp", "doc-copy-dst.tmp")?
(fs.read_text("doc-copy-dst.tmp") else "?") == "wolves\n"
fs.remove("doc-copy-src.tmp")?

Does something exist at path?

Total: no rows, no traps — a path the process cannot even ask about answers false rather than raising, which is what makes this the probe you write before a read_text and never the probe you rely on afterwards: between the two calls the answer can change, and only the row from the operation itself is authoritative (the check-then-use race is the caller's to avoid, not this function's to hide).

fstatfnpub

fn fstat(mut f: self.File) -> self.Stat ! {IoErrors} · regions (ρ1) -> ρ_caller

One metadata read on the open handle f.

[os.fs.fstat]. This is fs.size and fs.modified_ms and fs.is_dir and fs.is_file, answered together, off the handle a program is about to read anyway — one host call instead of four path resolutions.

The reason is a measurement, not a tidiness. wolf-lang#261: a static-file server was paying four path stats per request (is_dir, is_file, size, modified_ms) where nginx pays one open and one fstat, and the last two could not move into the program because nothing in this module answered off a handle. Now something does, and the four path calls stay exactly where they are for the callers that have a path and no handle.

Rows are the path stat's, so one handler serves both spellings: not_found, denied, io. On a HANDLE the hosts answer io for nearly everything — the entry is already resolved, so the misses the path calls have are behind it — and a closed or forged handle is io, this family's rule. A size or a time outside int is io, fs.size's rule. Never traps.

The one host difference is fs.open's, and it is stated. linux, macOS and freebsd open a directory read-only, so a File over a directory exists there and kind 1 is reachable. Windows refuses to open a directory as a file — fs.open answers denied, not this call — so on windows every handle this function ever sees is a file or a device, kind 1 never appears, and a server that classifies directories does it BY PATH with fs.is_dir, as it did before this call existed. That is a difference in what can be OPENED, not in what fstat reports, and no row here moves with the host.

mut f because a metadata read is a host call on the handle, and §14's stream rule has the call site spell it. The handle's read position is not disturbed.

Capability fs; refused at comptime (D33). Delegates to fs_fstat (s142) — both compiler lanes. The clause says every tier-1 host on every tier serves it, "the checked machine reads the same handle metadata the runtime does", and lupin still answers unsupported: the REFERENCE machine has no filesystem at all by design, so the whole fs tier is declined there rather than mocked, and that is a posture and not a release date. move_filefnpub

fn move_file(from: str, to: str) -> () ! {IoErrors}

Move the file at from to to.

Rows: not_found when from does not exist or to's parent directory does not, denied when the host refuses, io for any other host failure. Never traps.

The host rename is the fast path and copy-then-remove is the fallback — which is the other way round from every earlier pin, where the copy was the only path. The rename moves the directory entry without reading a byte, so a gigabyte within one filesystem costs the same as an empty file. Two of fs_rename's rows are the fallback's triggers rather than failures, and this function handles both:

  • cross_device — from and to are on different filesystems (EXDEV, ERROR_NOT_SAME_DEVICE), which no rename can do anywhere. The fallback is copy_file then remove, and because copy_file is a BYTE copy the fallback is a real fallback and not a text operation wearing a disguise.
  • exists — the destination is there and this host's rename will not replace it. unix replaces a file and an empty directory; windows refuses a directory outright. The fallback replaces it, so callers see one behaviour on every tier-1 target instead of the platform's.

It is not atomic and it does not claim to be. A host rename is atomic within a filesystem on unix; windows does not promise that, so the LANGUAGE does not promise it (there is no fs_rename_atomic) and neither does this function. On the fallback path it is plainly not atomic: a failure between the copy and the remove leaves both files, which is the same exposure this function has always had and is now the uncommon case rather than the only one.

The fallback's TRIGGER cannot be witnessed portably — a test would need two filesystems — so no test here reaches it, and the module header says so. Its body is copy_file followed by remove, both of which are tested.

Capability fs; refused at comptime (D33). Delegates to fs_rename, and to copy_file + fs_remove on the fallback.

Filestructpub

struct File { fd: int }

An open file: the host descriptor this process may read from or write to, according to how it was opened.

The field is an int because that is what the builtin tier hands out — a small non-negative index into the machine's file table, never a pointer, and never reused after close at this pin. Infostructpub

struct Info { kind: int, size: int, modified_ms: int, have: int, mode: int, nlink: int, uid: int, gid: int, blocks: int, dev: int, ino: int, rdev: int, atime_s: int, atime_ns: int, mtime_s: int, mtime_ns: int, ctime_s: int, ctime_ns: int, btime_s: int, btime_ns: int }

The full stat record of one path: what ls -l shows.

[os.fs.stat] (wolf-lang#625, #536). Twenty host words, named. The first three are Stat's, in its units — kind, size in bytes, modified_ms from the Unix epoch — and kind is finer here: 0 regular file, 1 directory, 2 anything the host does not name, 3 symbolic link, 4 fifo, 5 socket, 6 character device, 7 block device.

have says which words the host ANSWERED: bit i for word i of the clause's table (0 kind, 1 size, 2 modified_ms, 3 have, 4 mode, 5 nlink, 6 uid, 7 gid, 8 blocks, 9 dev, 10 ino, 11 rdev, 12–13 atime, 14–15 mtime, 16–17 ctime, 18–19 btime). A word whose bit is clear is 0 and is the host's refusal, by name — windows answers no mode, nlink, owner, blocks, identity or ctime; linux answers a birth time only where the filesystem keeps one. answered(info, word) reads the bit.

mode is the permission bits with set-user-id, set-group-id and sticky (0o7777), the file type being kind. blocks is in 512-byte units. dev and ino are the file's identity: two paths name one file when both agree — compare them, never order them. A time is a timespec: whole seconds from the epoch (negative before it) and nanoseconds in 0..999999999.

A new type, not a wider Stat: Stat's three fields are built by literal in programs that already exist, and a wider struct would refuse every one of them.

Statstructpub

struct Stat { kind: int, size: int, modified_ms: int }

What one metadata read on an open handle answers: a kind, a size and a modification time.

A typed value rather than the [kind, size, modified_ms] triple the builtin hands over. fs_fstat answers a List[int], and a caller reading got[0], got[1], got[2] is a caller who has to remember an ORDER — §14's rule is that when a builtin hands std a positional row whose meaning is the contract, std names the positions in a type. stat.size cannot be confused with stat.modified_ms; got[1] and got[2] can be, and silently.

kind is 0 for a regular file, 1 for a directory, 2 for anything else — a fifo, a socket, a device. It is an int and not an enum because std has no closed-enum vocabulary at this pin and a three-constant enum invented here would be a shape no other module shares; the numbers are the clause's own ([os.fs.fstat]) and the predicates below are what a program actually calls.

The unit rides in the field name for exactly the reason it rides in modified_ms's function name, and that doc carries the argument.
