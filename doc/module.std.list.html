pkg / std.list

std.list

std.list — the documented API surface of the language's List[T]: the growable sequence every other module hands back. Stability tier: core.

What is the language's and what is std's (sc02's structural finding, F-0011): List[T] is a language-blessed core type — both implementations provide it natively, the spec owns its semantics, and the three operations below stay the language's own:

  • construction: List[T]();
  • indexing: xs[i] reads, and an out-of-range index traps bounds in every profile (X3 posture) — every function here that names an index inherits exactly that trap;
  • iteration: for x in xs.

Everything else — this file — is std's. Functions take the container as their first parameter with an honest X1 mode: mut where mutation IS the operation, the bare read default everywhere else.

Two operations joined the language's list at the sc44 pins and they are worth naming because a learner reaches for them first: SLICING (xs[..n], xs[1..], [mem.list.slice]) runs on all three lanes now, and it is the language's, not std's. There is no list.prefix/list.suffix and there will not be one — §8 forbids a std name that shadows a working builtin — and there cannot be a list.take either, because take is a reserved word (E0008 on both machines: the ownership verb owns it).

THE METHOD SPELLINGS ARE NOT STD'S TO GIVE (wolf-std#25). A learner coming from chapter 5 writes (mut l).truncate(2) or l.remove(i) and gets "wolf cannot compile this yet — methods on generic std data" from the compiler and "List has no method truncate in this machine's std subset" from lupin. Both refusals are about the LANGUAGE's method surface on the builtin List, and std cannot extend it: this module is free functions over a container, by §8's rule, and list.truncate(mut l, 2) is the spelling it offers. All three of insert, remove and truncate are here, with bodies, with fenced doc examples that execute, and with three-lane ledger rows (list/insert_remove.lu, list/clear_truncate_fill.lu) — so the gap the issue found is a gap in what a learner is TOLD, not in what std ships. None of the three is written over the slice: the bodies rebuild through the private at, which predates slicing by nine sprints and stays because it is correct, and a rewrite would be churn against three green rows.

Regions (D10): every function allocates in the ambient region and no signature asks for one. The .in(r) targets are s37's plumbing, not this module's. s76 made that sentence true of the machine and not only of the API (the sc12 pin): a List allocates in the ambient region AT THE SITE, so a list built inside region r { } is freed with it and growth stays in the region it was born in. Nothing here changed to earn that, which is the point — a region-silent algorithm inherits its operands' homes, and now it does so in fact rather than in intention.

HISTORY, kept because two campaigns of bodies were shaped by it:

  • The single-read rule is DEAD (s72's D40, [mem.iter.excl], closed at the sc11 pin). wolfc's mem tier used to treat every read of a container place as a MOVE, so two read SITES over one binding in one body was E1001 (xs.len twice; xs.len then xs[i]; for x in xs then anything), and that is why every body here reads through len and the private at — one call per site — instead of projecting twice. Iteration takes a read claim over the loop's whole extent now, for no longer moves its iterable, and a write during the loop is E1013 statically and trap(exclusivity) dynamically (F-0005 and F-0014, both closed). The bodies keep their shape because they are correct and rewriting them would be churn; new code in this module does not need the ceremony.
  • The absence-spelling interim is retired: the tag is lowercase everywhere as of sc06 (F-0003 dead), and this header carried a half-renamed sentence about it — "none, not the convention's none" — for six sprints afterwards. A rename that touches 148 sites should have a reader on the prose too.

INTERIM SPELLINGS (each filed, flipped by the pin bump that fixes it):

  • The [T: Eq] family (contains, index_of, last_index_of, dedup, starts_with, ends_with) is NOT in this file: importing std.cmp for the bound would make every importer of std.list unsupported under wolfc's checked tier (its trait/enum items are not executable there — F-0012), on top of trait dispatch running nowhere (F-0002/F-0004). The six sit in std/x/list_eq/ with their bodies, and the stub comment below is their home here.

filterfnpub

fn filter[T](xs: prelude.List[T], keep: fn(T) -> bool) -> prelude.List[T] · regions (ρ1, -) -> ρ_caller

A new list holding the elements of xs for which keep holds, in their original order; xs is read, not consumed. The in-place sibling (retain) is not written: a returning filter is the combinator, and a mut twin would be a second name for one walk. Total: no error row, no traps beyond allocation.

[type.comb.set] (wolf-lang 4c046f15): the method xs.filter(keep) is this call ([type.method.resolve] step 2). Cost, as the clause states it: one fresh List[T] of at most xs.len in the ambient region, and xs.len calls of keep, plus one element copy per kept element — push's own, not one spelled here.

Why no copy is written. xs is a read parameter, so an element moved out of it is LENT and may not escape this call ([mem.tier0.mode.read], wolf-lang#366, in 0.2.15) — and the kept elements do escape, in the returned list. That clause says in its own words that it does not reach the builtin store which keeps a read argument inside its receiver; that is wolf-lang#385, ruled option 3 (s167, unreleased): push COPIES a non-Copy element by default, and push(take v) moves it. The default copy is exactly the copy this function needs, so writing copy x here would buy a second one. push's copy is deep on the native tiers ([mem.tier0.move.3], wolf-lang#384): a List element copies its buffer, a str element shares its immutable bytes, a scalar costs nothing. Nothing is lent out of this module either way, at this pin or at the next.

A new list holding f(x) for every x in xs, in order; xs is read, not consumed. The empty list maps to the empty list. Total: no error row, no traps beyond allocation and whatever f traps.

[type.comb.set] (wolf-lang 4c046f15): the method xs.map(f) is this call ([type.method.resolve] step 2), and eager ([type.comb.eager]). Cost, as the clause states it: one fresh List[U] of xs.len in the ambient region, and xs.len calls of f. A fallible f is par's alone ([conc.task.par]).

The one element here that this call OWNS, and the spelling it is owed. What this list holds is f's own return value, not an element moved out of xs, so nothing lent escapes ([mem.tier0.mode.read], wolf-lang#366); x is only LENT to f for the call, which is what a read parameter is for, and an f that hands its own argument back is the caller's site, not this one. Because f(x) is a temporary this activation owns, the right spelling under wolf-lang#385 (ruled option 3, s167, unreleased) is (mut out).push(take f(x)), which MOVES it where the default copies. It is not written yet because it does not exist yet: at wolf 0.2.14 both compiler rungs answer E1007 — push takes value as plain read, no mode is written for it (measured, F-0136), and that is a static refusal of this whole module, so every std.list row on both rungs would pay for it. It lands with the pin that carries s167, and the cost line above changes with it.

sort_byfnpub

fn sort_by[T](mut xs: prelude.List[T], less: fn(T, T) -> bool) · regions (ρ1, -) -> -

Sorts xs in place, stably, under less, where less(a, b) reads "a goes before b". Equal elements (neither goes before the other) keep their input order: the merge takes from the right run only when less(right, left) holds. less must be a strict weak order or the result is merely a permutation; std cannot check that and does not pretend to. Total: no error row, no traps beyond allocation and whatever less traps. std.sort's bottom-up merge, line for line. The result satisfies is_sorted_by(xs, fn(a, b) !less(b, a)).

[type.comb.set] (wolf-lang 4c046f15): the method (mut xs).sort_by(less) is this call, its receiver's mut spelled ([type.method.resolve], X1). Cost, as the clause states it: stable, O(n log n) calls of less, O(n) scratch in the ambient region, and no copy at all: the receiver is mut, not read, so no element here is lent and the sorted elements go back to the caller's own list ([mem.tier0.mode.read], wolf-lang#366). The returning twin sorted_by pays the copies instead, because its receiver is read.

Why the relation is bool and why std.sort keeps its own. The clause rules it: std.sort.sort_by takes a cmp.Ordering, and at wolf 0.2.14 / lupin 0.1.36 it runs on no lane (re-measured for this function: lupin declines the enum's dynamics at resolve, the checked machine declines std.cmp's module items, the native rung finds .is_lt() untyped; F-0029). std.sort's Ordering pair keeps its qualified spelling; the method is this one. Same mode, same stability, same algorithm; the comparator's type is the one difference, and it is stated on both.

Call shape (a prose example, witnessed by tests/list/sort_by_tier.lu on all three lanes): fn shorter(a: str, b: str) -> bool { a.len < b.len } … then list.sort_by(mut words, shorter). Not fenced: the call is a statement, and §4's extractor reads a line holding the relation's < as an assertion. sorted_by's example is fenced and shows the same order. Do not name a top-level fn less in a program that passes a different relation: the checked machine calls it instead of the argument (F-0134, wolf-lang#400).
